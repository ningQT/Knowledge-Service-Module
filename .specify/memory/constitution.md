# KSM 项目宪法

<!-- 本文件为 KSM（Knowledge Service Module，知识服务模块）的项目宪法，是项目所有开发、评审与文档活动的最高治理依据。 -->

## 核心原则

### I. 先确认，后写入（不可协商）

- 任何对项目文件的创建、修改或删除，必须先说明「任务目标、影响范围、最小修改边界、验证方式」，并在获得用户明确确认后方可执行。
- 未经确认，不得进入实现或修改阶段。
- 只处理本次任务明确要求的内容，不得修改无关文件、代码、配置或文档。

### II. 最小修改与复用优先

- 修改范围严格以任务明确要求为边界，不得顺手优化、扩大范围、大规模重构或擅自调整架构。
- 不得擅自改变接口、业务逻辑、交互、配置、数据结构、兼容逻辑、项目结构或现有行为。
- 优先复用已有组件、公共模块、工具函数与既有实现；不复用时必须书面说明原因。

### III. 文档全面中文化

- 所有文档（含 Spec Kit 的 spec / plan / tasks / constitution 等产物）、流程说明、阶段说明、注释、状态文档一律以中文撰写。
- Spec Kit 官方模板虽为英文，落地到本项目的所有实际文档必须全中文，不得沿用英文模板正文。
- 代码、命令、路径、变量名、接口名、错误信息、日志、第三方库/框架/工具与官方专有名词可保留原文。
- 所有源代码、配置、文档文件必须使用 UTF-8（不带 BOM）编码保存；写入含中文内容的文件后必须立即校验无乱码。

### IV. 注释规范

- Python 使用 Google 风格 docstring（reStructuredText 格式，含 Args / Returns / Raises 章节）；前端 JavaScript / TypeScript 使用 JSDoc（含 @param / @returns / @throws 标签）。
- 所有注释统一使用中文；注释应说明「为什么」而非「是什么」，避免冗余和显而易见的描述。
- 关键逻辑、边界条件、复杂分支、算法步骤、TODO / FIXME 等场景必须添加行注释。

### V. 验证如实

- 修改完成后必须使用项目已有测试、构建、类型检查、lint 或本地运行方式验证。
- 不得声称运行了未实际运行的测试；验证失败时必须如实说明，先定位并修正，不得继续堆叠后续改动。
- 无法运行测试时，必须说明原因，并列出已完成的静态检查或人工核验。

## 工程规范

- **技术栈固定**：后端为 Python 3.11+ / FastAPI / SQLite（FTS5）/ 本地文件系统；前端为 React 19 / TypeScript / Vite / Tailwind CSS / shadcn/ui / Zustand / React Flow。沿用既有选型，不得引入新框架、新组件库或新样式体系；确需新增时必须说明原因、影响范围与复用策略。
- **敏感信息**：密钥、令牌、账号密码、生产私密配置等敏感信息不得写入代码、配置、文档或日志；日志不得输出敏感信息。
- **临时产物清理**：临时测试脚本、调试文件、临时目录、临时输出必须在任务结束前清理。
- **接口与配置变更**：错误处理保持项目现有风格；必须改变请求/响应结构、状态码或持久化格式时，须说明兼容策略、迁移影响、默认值、影响范围与回滚方式。

## 文档治理

- **方案文档**：方案、计划、调研、设计类文档统一置于根目录 `task_plan/` 下，命名遵循 `YYYY-MM-DD-中文描述.md`；已完成或已废弃的方案文档不得删除（废弃须在标题或文件名标注 `[已废弃]` 并说明替代方案）。
- **状态文档**：`PROJECT_STATUS.md` 用于本地跨会话继承长期项目上下文，不提交到版本仓库；仅记录有长期价值的信息，不写成开发流水账；创建、修改、删除均须先说明理由并获用户确认。
- **忽略规则**：`.gitignore` 必须包含 `PROJECT_STATUS.md`；缺失时须说明并等待确认后再修改。

## 治理

- 本宪法优先于其他实践与默认行为；与全局 CLAUDE.md、项目 CLAUDE.md（若存在）产生冲突时，以更严格的约束为准。
- 修订须记录修改原因与影响范围，并按语义化版本递增：MAJOR（不兼容的原则删除或重定义）、MINOR（新增原则/章节或实质性扩展）、PATCH（措辞、澄清、非语义性修正）。
- 版本号、批准日期、最后修改日期均以 ISO 8601（YYYY-MM-DD）格式记录。
- 所有 PR 与评审必须核验对本宪法的合规性；引入的复杂度必须有正当理由。
